PowerContext 应用示例 · Qoder 开发

科研实验续作助手

实验跨多天、多人、多台机器进行时，"上次做到哪、结论是什么、下一步做什么"往往散落在聊天记录和终端输出里。 本应用把每次实验进展作为可检索的 Memory 写入 PowerContext，重新打开时按实验自己的 Scope 召回原文。

真实痛点

重启后失去上下文

隔天或换机器继续实验时，需要翻聊天记录、shell history 和散落的日志才知道上次改了哪个参数、哪组结果可信。

多人多实验互相污染

把进展写进同一个笔记或同一个向量库里，A 实验的结论会被 B 实验的提问召回，恢复出来的"上次进展"其实属于另一个项目。

自由文本无法稳定取回字段

进展和下一步里充满中文分号、字段名、引号、HTML 标签和换行。用分隔符拼接的记录会在这些字符上拆错字段，恢复出错误内容。

"连上了"不等于"记住了"

只展示服务连接成功的演示没有价值。必须能看到真实的写入响应、召回内容和 entry 身份，并且能区分无记忆、服务不可用和接口错误。

核心功能

  • 主动保存为 decision Memory 页面填写实验名称、当前进展和下一步，由后端调用真实 POST /v1/memory/remember 写入当前实验的 Scope，不使用 localStorage 或本地 JSON 代替记忆。
  • 按实验独立 Scope 召回 提问时组合可检索锚点 实验进展 与用户原话，通过 POST /v1/context/prepare 取回原文；不同实验绑定的 Scope 不同，互不召回。
  • 最后一次成功保存一定能取回 相关度召回是截断的候选集，应用再用同一 Scope 的记忆清单补全比较，并按保存序号排序，避免旧记录盖过最新保存。
  • 字段逐字保留 进展文本用带 实验进展： 前缀的结构化编码保存，中文分号、字段名、引号、HTML 样式文本与换行原样往返；旧的分隔符格式记录仍可解析，无法解析的按原文展示而不是报"没有记忆"。
  • 重启恢复 实验与 Scope 的映射持久保存在服务端，重启进程后按同一 Scope 再次召回，恢复同一条 entry 的进展与下一步。
  • 三种失败状态分开展示 无记忆、服务不可用（503）与接口错误（502）各自返回明确状态并在页面显示，绝不伪装成成功召回。
  • 展示前转义 页面只用 textContent 写入召回内容，原始记忆文本按字面显示，不会被当作标记执行。

架构

浏览器页面  web/index.html + web/app.js
    │  fetch（无凭据、无 localStorage 记忆）
    ▼
本机后端  backend/server.py（Python 3.11+ 标准库 ThreadingHTTPServer）
    ├── backend/config.py        读取 POWERCONTEXT_URL / POWERCONTEXT_TOKEN(可选) / POWERCONTEXT_SCOPE(可选)
    ├── backend/store.py         实验 ↔ Scope 映射（data/experiments.json，原子写入）
    │                            以及进展文本的结构化编解码（"实验进展：" + JSON 文档）
    └── backend/powercontext.py  OpenAPI 客户端（urllib.request）
              │
              ├─ POST /v1/scopes                为每个实验创建独立 Scope
              ├─ POST /v1/memory/remember       kind=decision，写入实验进展（≤8192 UTF-8 字节）
              ├─ POST /v1/context/prepare       按 Scope + 问题召回，返回组装好的历史上下文
              └─ POST /v1/memory/entries/list     同一 Scope 的记忆清单，用于补全被截断的候选

状态区分：连接失败 → 503 service_unavailable；服务返回错误 → 502 api_error；
Scope 内没有进展记忆 → 200 no_memory；召回到条目 → 200 recalled + 真实 entry 身份。

凭据由后端环境变量或受保护的本地配置提供，不写入前端、源码或公开材料。公开站点不携带后端服务， 实际体验按运行与验证说明在本机完成。

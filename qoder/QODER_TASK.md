# 交给 Qoder 的项目任务书

请在当前 `qoder/` 目录中完成项目的主要设计、编码、调试和验证。保留本次及后续关键对话记录。不要编造运行结果、用户反馈或开发记录。完成本地验证后，先展示结果；由项目所有者审核并在个人账号中通过 Qoder Sites 发布。

## 真实问题

科研实验经常跨多天、多人或多台机器进行。重新开始时，需要翻聊天记录和终端输出才能知道上次做了哪组实验、得出了什么结论、下一步要做什么。请实现“科研实验续作助手”，解决实验进展记录与后续恢复的问题。

## 必须实现的主流程

1. 用户填写实验名称、当前进展和下一步，主动点击保存。
2. 后端通过 PowerContext `POST /v1/memory/remember` 保存为当前实验 Scope 的 `decision` Memory。不要在前端直接写入服务凭据，不要用浏览器 localStorage 或本地 JSON 替代 PowerContext 的记忆功能。
3. 用户重新打开项目或询问“上次进行到哪里，下一步是什么？”，后端通过 `POST /v1/context/prepare` 按当前 Scope 和问题召回记忆。
4. 页面明确展示召回的实验名称、进展和下一步，以及来自 PowerContext 的 entry ID、entry version ID 或召回内容。不得把固定示例文本当作召回结果。
5. 应用重启后使用同一 Scope，仍能恢复已保存内容。无记忆、服务不可用和接口错误要分别显示，不得伪装成成功召回。
6. 每个实验使用独立 Scope，避免不同项目互相召回。展示原始输入前做 HTML 转义；不要记录 token、密码或真实私人文档。

未配置向量模型时，中文问题可能与记忆原文没有共同词元。保存进展时使用统一的可检索文本前缀 `实验进展：`；召回时将 `实验进展` 与用户问题组合，同时保留用户问题用于相关度排序。请用实际服务验证此行为，而不是假定 FTS 支持中文语义匹配。

## 工程约束

- 优先后端使用 Python 3.11+ 标准库，前端使用 HTML/CSS/JavaScript，避免不必要的框架和大型依赖。
- 后端配置项：`POWERCONTEXT_URL`、`POWERCONTEXT_TOKEN`（可选）、`POWERCONTEXT_SCOPE`。提供占位配置示例，不提交真实凭据。
- 使用仓库 `openapi/powercontext.yaml` 中的请求和响应契约，先阅读现有实现再写接入代码。
- 项目自身提供清晰的启动命令、停止命令、配置说明和至少一组验证样例。
- 自动化验证必须发送真实 HTTP 请求并断言写入、召回和重启恢复；错误时应以非零状态退出。静态连接检查不等于功能验证。
- 遵循现有仓库规范，不修改 PowerContext 的基准、评分脚本、测试输入和期望结果。
- 复用现有 `verify_powercontext.py` 做独立服务验证；还要验证项目自身的页面和 API 主流程。

## Qoder Sites 网站

在 `site/` 制作可静态发布的项目展示网站，包含：项目简介、真实痛点、核心功能、架构图或文字架构、实际演示截图或录屏链接、源码仓库链接、运行与验证说明入口。网站只用于展示，不要把本地 PowerContext 地址或访问 token 暴露给公众。若网站提供体验入口，必须有可公开访问且安全部署的后端；否则明确说明按运行说明本地体验。

网站必须能通过 Qoder Sites 发布为“任何人都可访问”。发布前在本地静态服务器检查所有链接。发布操作由项目所有者审核后进行，保留 Qoder 的发布过程记录。
